## 1. 프론트 변경분을 반영해 달라는 요청을 받았을 때

### Step 0. 범위 파악

- 사용자가 어떤 화면/무엇이 바뀌었는지 설명했으면 그대로 근거로 삼는다.
- 불명확하면 `git diff` / `git status`로 `src/frontend/`(현재 구조: `index.html` + `js/data.js`
  + `js/render.js` + `js/app.js`, SPA 렌더 함수 기반 — 화면별 별도 HTML 파일이 아님) 변경분을
    직접 확인한다.
- **절대 스펙 문서(화면설계서.md)만 보고 작성하지 않는다** — 실제 구현(`render.js`의 렌더 함수,
  `data.js`의 mock 데이터/필드 라벨/버튼 문구)이 스펙과 다를 수 있다(2026-08-13 세션에서 실제로
  다수 발견됨: SCR-006 명칭, SCR-003 경고배너, 화면 개수(14개 vs 실제 15개=SCR-001~014+
  MTRM-MAIN), 관리자 3중 표시 등). `Agent`(Explore)로 `src/frontend/`를 조사해 as-built 인벤토리를
  먼저 만드는 것을 권장한다.

### Step 1. GNB(사이드바) 확인

- `js/data.js`의 `NAV`/`FEATURE_FLAGS` 배열이 **실제 사용자에게 노출되는 화면 목록의 근거**다.
  코드가 존재해도 `NAV`에서 빠져 있거나(`DASH-AUTO`/`DASH-MTRM`처럼 고아 화면) 기본 비노출
  플래그(`showFlowMapInNav` 등)로 숨겨진 화면은 이번 작업 범위에서 **제외**한다(사용자에게 그
  이유를 안내).
- GNB 순서·그룹(공정 자동화 현황 / 중장기 방향성 공유)도 `NAV`를 그대로 따른다. 하위 메뉴
  (`NAV_CHILDREN`)가 있으면 들여쓰기로 표현한다.
- **관리자 화면 색상 구분은 2026-08-14부로 폐지됨.** 과거에는 관리자 화면(`SCREENS[id].admin === true`)에 3중 시각 표시(① GNB 항목 옆 보라색 "A" 배지 ② 상단 breadcrumb 옆 "관리자" 배지
  ③ 본문 영역 좌측 4px 보라색 강조 바)를 적용했으나, 사용자 지시로 문서 전체(7개 관리자 화면
  자기 페이지 + 모든 페이지의 반복 사이드바)에서 제거했다. **새 관리자 화면을 추가할 때도 이
  색상 마커를 되살리지 않는다** — `admin` 플래그 자체는 판별용으로만 쓰고(예: Description의
  "관리자 화면 연동" 문구, 필요시 텍스트 라벨), 시각적 색상 구분은 넣지 않는다.
  `screens_common.py`의 `render_sidebar`/`render_topbar`/`admin_content_wrap`은 이미 no-op으로
  수정되어 있으니 그대로 호출해도 안전하다.

### Step 2. 화면별 와이어프레임 작성

- 상단바(PNDES 로고+breadcrumb+사용자정보)와 좌측 GNB는 모든 화면이 공유하는 셸이다. 화면마다
  다시 그리지 말고 템플릿 함수로 생성한다.
- 본문(메인 콘텐츠)은 실제 `render.js` 렌더 함수의 마크업 구조를 참고해 우리 프로젝트의 저충실도
  스타일(테두리 1px #ccc, 배경 #f2f2f2/#fff, 폰트 12px 위주)로 다시 그린다 — 픽셀 단위로 그대로
  베끼지 않는다. 표/필터바/버튼/카드그리드/간트차트/모달 미리보기 등 컴포넌트 빌더 재사용
  (`screens_common.py` 참고).
- 새로운 컴포넌트 유형(카드 그리드, 간트, 등록 모달, 폼)이 필요하면 기존 스타일 톤에 맞춰
  새로 만들고 `screens_common.py`에 추가해 재사용성을 높인다.

### Step 3. Description(상세설명) 작성

- `화면설계서_Description작성가이드.md`의 최종 정책을 그대로 따른다(요약: 영역=1행, NO는
  영역번호만, 요소 1개면 번호 생략, 영역명/요소명/NO 볼드, 노출조건→입력조건→출력조건→
  인터랙션→예외Case→관리자연동→BE연동 순, 없으면 생략).
- **팝업/모달은 반드시 "팝업 영역"으로 문서화**한다 — `render.js`에서 `data-action="open-modal"`
  로 열리는 모든 모달(및 `data.js`의 `MODALS` 정의)을 해당 화면의 마지막 영역으로 추가한다.
  트리거 조건과 필수 입력 필드(`*`)를 `입력조건`에 명시한다.
- **Description 텍스트만으로 끝내지 않는다(2026-08-14 확립).** "팝업 영역" 텍스트만 쓰고 실제
  팝업 와이어프레임 페이지를 만들지 않으면 html/pdf/ppt 어디에도 팝업의 실제 모습이 노출되지
  않는다는 지적을 받은 적이 있다 — 팝업마다(또는 성격이 비슷하면 묶어서) `screens_common.py`의
  `popup_page()`로 **별도 screen-section 페이지**를 만들어 부모 화면의 마지막 페이지 바로 뒤,
  다음 화면 앞에 삽입한다. 구성: 부모 화면의 배경(TOP BAR+SIDEBAR+MAIN CONTENT, 단
  `.indicator`/`.indicator-el` 배지는 제거)을 `opacity:0.32; filter:grayscale(35%);`로 흐리게
  깔고, 그 위에 반투명 검정 오버레이(`rgba(20,20,20,0.45)`)와 중앙 정렬 모달 카드를 얹는다.
  모달 필드는 `field_row()`로 만들고, 모달을 가리키는 영역 인디케이터(보통 "1")는 모달 카드에
  **중첩**시킨다(아래 Step 4의 이유와 동일 — wireframe-wrap 기준 고정 좌표로 별도 배치 금지).
  상단 탭 네비게이션에도 각 팝업 페이지 버튼을 추가한다.
- **팝업 배경(딤 처리된 부모 화면 스냅샷)은 부모 화면의 "1페이지(1스크린)" 분량만 담는다
  (2026-08-18 사용자 지시로 확립).** 모달 팝업이 뜬 상태에서 뒤에 흐리게 보이는 배경은 부모
  화면 전체가 아니라, 그 화면의 **표준 1페이지 크기**(이 문서의 다른 모든 화면 페이지와 동일한
  `.wireframe-wrap` 크기 — PDF 기준 약 1240px 폭 렌더의 1스크린 분량)만큼만 잘라서 보여주면
  충분하다. 즉:
  - 부모 화면에 이어붙임(cont) 페이지가 있어도, 팝업 배경에는 **원본(첫) 페이지 내용만**
    가져온다 — cont 페이지의 오버플로우 데이터까지 욱여넣어 배경을 늘릴 필요 없다.
  - 부모 화면 안에 `max-height`+`overflow:auto`(Step 4-1 `scroll-wrap-detail` 류)로 세로
    스크롤 처리된 표/패널이 있다면, 팝업 배경에도 **그 스크롤 wrapper와 동일한 `max-height`를
    그대로 유지**한 채 가져온다 — wrapper를 걷어내고 전체 행을 펼쳐서 렌더링하면 배경이 부모
    화면 자체보다도 커져버려 이 원칙(1페이지 분량 유지)에 위배된다.
  - 결과적으로 팝업 페이지 자체(딤 배경 + 모달)의 전체 크기도 이 문서의 다른 일반 화면
    페이지와 동일한 1페이지 표준 크기를 벗어나지 않아야 한다 — 팝업이라고 해서 페이지가
    유독 커지거나 스크롤 가능한 형태로 늘어나면 안 된다.
  - **사고 사례(2026-08-18)**: SCR-001의 팝업 3종(`scr-001-popup-7-1/7-2/7-3`)이 배경으로
    가져온 "공정별 상세" 표에서 원본 SCR-001 페이지가 쓰는 `scroll-wrap-detail`
    (`overflow:auto; max-height:520px;`) wrapper를 빠뜨리고 `overflow-x:auto`만 남긴 채
    전체 19행을 펼쳐서 렌더링했다. 그 결과 팝업 페이지 높이(1671px)가 표준 1페이지 높이
    (897~1044px)를 크게 초과했고, 심지어 원본 SCR-001 페이지 자체(1044px)보다도 커졌다.
    수정: `overflow-x:auto` 단일 wrapper를 원본과 동일한
    `<div style="position:relative; border:1px solid #ccc;"><div class="scroll-wrap-detail"
    style="overflow:auto; max-height:520px;">...</div>(스크롤바 장식 오버레이 2개)</div>`
    구조로 되돌려 표준 1페이지 높이로 복원했다.
- **PPT에서 배경-모달 텍스트 겹침 방지(2026-08-18 확립, 필수):** 팝업 페이지의 딤 처리 배경
  래퍼(위 문단의 `opacity:0.32; filter:grayscale(35%); pointer-events:none;` div)에는 반드시
  `class="popup-backdrop"`를 붙인다(`popup_page()` 헬퍼는 이미 이 클래스를 자동으로 붙임 —
  헬퍼를 안 쓰고 직접 마크업을 작성할 때만 신경 쓰면 됨). **이유**: HTML/PDF는 브라우저가
  opacity·absolute 오버레이를 실제로 렌더링해 배경이 흐리게 깔리고 그 위에 불투명 모달이 덮여
  자연스럽게 보이지만, PPT 변환(`sbpptxRenderElement`)은 `section.querySelectorAll('*')`로
  섹션 내 모든 요소를 z-index/오버레이 관계 없이 평면적으로 순회하며 각 텍스트 리프를 그
  요소의 실제 화면 좌표에 개별 텍스트박스로 찍는다. 배경(표/버튼/필드 등)과 그 위에 얹힌 모달
  폼이 정확히 같은 좌표 공간(모달이 `position:absolute; inset:0`)을 차지하므로, opacity 필터링
  없이는 배경 텍스트와 모달 텍스트가 같은 위치에 100%까지 겹쳐 출력된다(2026-08-18 실측: 팝업
  페이지 24개 슬라이드에서 최대 100% 겹침 다수 확인 — 이게 사용자가 "PPT만 Description/본문
  텍스트가 겹치거나 잘려 보인다"고 재차 지적한 근본 원인이었다. `opacity:0.32`는 0이 아니므로
  `sbpptxRenderElement`의 `if (parseFloat(style.opacity)===0) return;` 가드로는 걸러지지
  않는다). **수정**: `downloadPPTX()`의 1차/2차 패스 순회 필터와 `sbpptxRenderElement` 진입부
  양쪽에 `el.closest('.popup-backdrop')`이면 완전히 스킵하는 조건을 추가했다(이중 방어) —
  이 파일을 그대로 이어서 수정하는 한 유지되지만, export `<script>` 블록을 외부 템플릿에서
  통째로 재주입하면 사라지므로 그 경우 재적용 필요(심볼: `popup-backdrop`, `downloadPPTX`
  1차/2차 패스, `sbpptxRenderElement` 진입부 가드). **검증**: python-pptx로 실제 다운로드한
  PPTX의 슬라이드별 텍스트박스 좌표를 뽑아 겹침 비율을 계산하는 방식이 가장 확실하다(HTML/PDF
  스크린샷으로는 이 문제가 애초에 재현되지 않으므로 육안 확인 불가 — 반드시 PPTX를 열어
  도형 좌표로 검증).
- 예외 Case에 alert/toast/confirm 문구가 있으면 반드시 원문 그대로("alert: \"...\"" 형식) 적는다
  — 부록 페이지(4절)가 이 문구를 그대로 긁어간다.

### Step 4. 인디케이터(번호 지표) 배치

- **절대 생략하지 않는다** — 2026-08-14 세션에서 화면 전체 교체 시 인디케이터 삽입을 빠뜨려
  SCR-001 외 모든 화면에 인디케이터가 아예 없어지는 사고가 있었다. 화면 콘텐츠를 갈아끼울 때마다
  인디케이터가 살아있는지 `grep -c 'class="indicator"'`로 반드시 재확인한다.
- 위치는 감으로 정하지 말고 **Playwright로 실측**한다: 각 영역(NO)에 대응하는 본문 상위 블록의
  `getBoundingClientRect()`를 wireframe-wrap 기준 상대좌표로 구해, `top - 9px`, `left - 22px`
  근처에 배치한다(텍스트와 겹치지 않는지 스크린샷으로 반드시 확인).
- **관리자 화면 주의**: 본문이 좌측 강조 바 wrapper `<div>` 하나로 한 번 더 감싸져 있으므로,
  `main.children.length === 1`이면 그 자식으로 한 번 더 들어가야 진짜 콘텐츠 블록들이 잡힌다.
- **팝업 페이지의 인디케이터는 팝업 안에서 새로 번호를 매기지 않는다 — 그 팝업을 연 트리거
  요소의 번호를 캔버스 배지와 Description NO 양쪽에 그대로 이어받는다**(2026-08-25 확정,
  `check_popup_indicator_inheritance`/R22로 코드화). 예: SCR-001에서 "+ 공정 등록"(5-1) 버튼이
  여는 팝업이면, 그 팝업 페이지의 캔버스 배지도 `5-1`, Description도 `NO=5-1`이어야 한다 —
  팝업이 새 화면이라고 해서 `1`부터 다시 매기면 안 된다(과거 19개 팝업 전원이 이 실수를 저지른
  이력 있음). 트리거가 "행 삭제 클릭"처럼 특정 서브요소 번호가 없는 경우는 상위 화면에서 그
  동작을 설명하는 영역(NO)의 번호를 그대로 쓴다(예: 목록 표의 "삭제" 열이 NO=2 요소 2-3이면
  삭제 확인 팝업도 `2-3`). "팝업이라 위치를 못 짚으니 생략해도 된다"는 뜻이 아니다 — 트리거를
  못 찾겠으면 생략하지 말고 상위 화면 Description을 다시 읽어서 반드시 번호를 확정한다.
- **요소별 인디케이터(2026-08-14 도입, 같은 날 배치 방식이 한 차례 더 수정됨)**: 영역에 요소가
  2개 이상이면, 기존 영역(NO) 인디케이터 `.indicator`(주황 원)는 그대로 유지한 채로 요소 각각의
  위치에 `.indicator-el`(빨간 원, 흰 테두리, `<span>N-1</span>` 라벨은 Description의 요소번호와
  동일하게 "N-1", "N-2"…)을 추가로 배치한다. 두 인디케이터는 공존하며 서로 대체하지 않는다.
  요소가 시각적으로 뚜렷한 형제 블록(탭, 버튼 그룹, 유틸 아이템, 나란한 패널 등)일 때만
  적용하고, 팝업처럼 고유 위치가 없는 요소는 생략한다.

  **⚠️ 배치 방식은 반드시 "타겟의 중첩 자식"으로 한다 — `.wireframe-wrap` 기준 고정
  top/left 형제 요소로 만들지 않는다.** 처음 도입할 때 고정 좌표 형제 요소 방식으로 만들었다가,
  실제 PPT/PDF 다운로드에서 위치가 어긋나고(5번 영역) 일부는 아예 안 보이는(6번 영역) 문제가
  발견되어 재작업했다. **원인**: 이 문서의 화면 레이아웃은 유동폭 그리드(`1fr 380px`)라서 같은
  화면도 HTML 뷰(임의 폭) / PDF(`applyPrintScaling`이 강제하는 약 1240px) / PPT
  (`downloadPPTX`가 강제하는 1680px) 세 렌더 폭이 서로 다르다. 고정 px 좌표는 그중 딱 하나의
  폭에서 측정한 값이라 나머지 두 곳에서는 진짜 타겟 위치와 어긋나고, PPT는 심하면 슬라이드
  경계 밖으로 밀려나 `sbpptxRenderElement`가 그 요소를 통째로 스킵해버린다(6번 영역 하위요소가
  PPT에서 안 보였던 이유). 사이드바 바로 옆(고정 190px 폭 뒤)처럼 폭 변화와 무관한 위치만
  예외적으로 고정 좌표가 안전하다(SCR-001의 1-1/1-2 탭 배지가 그 예).

  **표준 구현**: `screens_common.py`의 `field_row`/`el_badge`/`make_el_badge_wrap` 참고,
  또는 타겟 요소의 `style` 앞에 `position:relative; `을 추가하고 그 안에
  `<div class="indicator-el" style="bottom:-9px; right:-6px;"><span>N-1</span></div>`을
  마지막 자식으로 넣는다(코너에 살짝 겹쳐 매달리는 배지 형태 — bottom/right 조합, 반대편이면
  top/left). 배경이 흐린 텍스트 span(예: 상단 유틸 바 "홍길동 님")처럼 인라인 요소에 붙일 때는
  `display:inline-block;`도 함께 준다. **인라인 텍스트(예: 표 행의 "수정"/"삭제" 액션 텍스트)에
  붙일 때는 반드시 `<span style="position:relative; display:inline-block; ...">텍스트<div
  class="indicator-el" ...><span>N-1</span></div></span>` 형태로, `.indicator-el`이 그 span의
  직접 자식이 되게 한다** — `display:inline-block`을 빠뜨리면 HTML/PDF 화면(실브라우저 렌더)에서는
  문제없이 보여도 PPTX 변환에서만 배지 텍스트가 조용히 사라진다(아래 PPT 상호작용 문단 및 Step 9
  참고, 2026-08-18 SCR-002 2-2/2-3 인디케이터 사고).

  **Description에 새 요소(NO-N)를 추가할 때는 캔버스 인디케이터도 반드시 같이 추가한다.**
  Description 텍스트만 쓰고 대응하는 `.indicator-el` 배지를 캔버스에 빠뜨리는 사고가
  반복됐다(2026-08-18, SCR-002의 NO=2가 설명하는 2-1/2-2/2-3 요소 전체에 인디케이터가 아예
  없어서 NO=1만 1-1/1-2/1-3 배지가 있는 비대칭 상태로 남아있었음 — Description 작성 시점과
  인디케이터 배치 시점이 분리된 여러 세션에 걸친 작업이라 발생). Description에 요소번호(N-1,
  N-2…)가 등장하면 그 화면의 모든 반복 페이지(원본+이어붙임 cont 페이지)에서 `grep -c
  'indicator-el'` 등으로 요소 개수만큼 배지가 실제로 존재하는지 교차 확인한다.

  **PPT 내보내기 엔진과의 상호작용(중요, 잊으면 재발함)**: `.indicator-el`을 타겟의 자식으로
  중첩시키면 `downloadPPTX`의 `sbpptxIsTextLeaf`/`sbpptxRichRuns`가 배지의 숫자 텍스트("5-1" 등)
  를 부모의 라벨 텍스트로 착각해 합쳐버리거나(`"+ 공정 등록5-1"`처럼 깨짐) 부모 자체가 텍스트
  리프로 인식되지 않아 라벨이 통째로 사라질 수 있다. 이 문서(`05.리포트/화면설계서_...html`)의
  `<script>` 내 `sbpptxIsTextLeaf`와 `sbpptxRichRuns`는 이미 `child.classList.contains ('indicator-el')`이면 완전히 무시하도록 수정되어 있고, `downloadPPTX`의 1차/2차 렌더 패스
  분기도 `.indicator-el`을 `.indicator`와 동일하게 최상위 레이어로 옮기도록 수정되어 있다 —
  **이 파일을 그대로 이어서 수정하는 한 자동으로 유지**되지만, 만약 export `<script>` 블록을
  외부 템플릿에서 통째로 재주입(예: `sb-creator-pptx`류 inject 도구 재실행)하게 되면 이 세 군데
  수정이 사라지니 재적용해야 한다 — 심볼: `sbpptxIsTextLeaf`, `sbpptxRichRuns`,
  `downloadPPTX` 내 "1차 패스"/"2차 패스" 주석.

  적용 후에는 반드시 세 가지 렌더 폭(HTML 임의 폭 / PDF ~1240px / PPT 1680px)에서 스크린샷 또는
  Playwright로 `document.documentElement.style.width`를 강제 변경해가며 겹침 여부를 확인한다.

### Step 4-1. 스크롤 가능 테이블(상하/좌우) 표현 (2026-08-15 도입)

- 실 구현(`render.js`)에서 `.scroll-panel`/`sticky-head` 등으로 세로 스크롤이 있거나, 테이블
  컬럼 수가 많아 가로 스크롤이 생기는 영역은 **와이어프레임에서도 스크롤 가능하다는 사실이
  시각적으로 드러나야 한다** — 표를 그냥 길게/넓게 그리고 끝내지 않는다.
- **세로 스크롤(고정 높이 + sticky 헤더)**: 실제 구현의 `max-height` 값을 그대로 참고해
  와이어프레임 표 wrapper에 `max-height:520px; overflow-y:auto;`(예시, 실측값 사용)를 주고,
  헤더 `<thead>`에 `position:sticky; top:0;`를 준다. 정적 캡처(PDF/PPT)에서는 스크롤 동작
  자체를 재현할 수 없으므로, wrapper 우측 안쪽에 `▼ 스크롤` 같은 작은 텍스트 배지를 추가해
  "이 영역은 스크롤됩니다"를 시각적으로 표시한다(`screens_common.py`에 헬퍼 추가 권장).
- **가로 스크롤**: `overflow-x:auto`가 있는 `simple_table()` 기본 동작을 그대로 쓰되, 컬럼이
  실제로 뷰포트를 넘어가는 케이스는 표를 실제 컬럼 수만큼 넓게 그려서 가로 스크롤바가 보이도록
  하고, wrapper 하단에 `◀ 좌우 스크롤 ▶` 배지를 추가한다.
- Description에는 해당 영역(또는 요소)의 **인터랙션** 항목에 "세로/가로 스크롤 가능(고정
  헤더/열 유지)"처럼 실제 구현 동작을 명시한다. 스크롤 대상 열이 고정(freeze) 열인 경우
  ("NO/공정명 열은 가로 스크롤 시에도 고정") 그 사실도 함께 적는다.
- 스크롤 영역 자체를 가리키는 영역 인디케이터(NO)는 wrapper 전체에 배치하고, 스크롤 안의
  개별 열/행이 별도 요소로 뚜렷이 구분되면(예: 고정 열 vs 스크롤 열) 요소 인디케이터
  (`.indicator-el`)로 추가 표시한다.

### Step 4-2. 상위 페이지 팝업이 하위 페이지에도 있을 때의 NO 번호 규칙 (2026-08-15 도입)

- 화면 A(상위)에서 트리거되는 팝업을 `popup_page()`로 별도 페이지화할 때, 그 팝업이 화면 A의
  Description에서 이미 특정 영역 NO(예: NO=5 "팝업 영역")로 설명되어 있다면, **팝업 자신의
  screen-section 페이지(하위 페이지) Description에서도 그 팝업 전체를 가리키는 NO는 상위
  페이지와 동일한 번호를 그대로 사용한다** — 하위 페이지에서 새로 1부터 매기지 않는다.
  예: SCR-001 Description의 NO=7 "팝업 영역"에서 "공정 등록" 모달을 설명했다면, 공정 등록
  모달의 별도 팝업 페이지(`scr-001-popup-7-1` 등, 파일명 서픽스에도 상위 NO를 반영)의
  Description NO도 `7`로 시작한다.
- 팝업 페이지 안에서 그 팝업 자체에 요소가 여러 개면(예: 필드 그룹, 버튼 그룹) 상위 NO에
  요소번호를 붙인 `N-1`, `N-2` 형식을 그대로 이어서 쓴다(Description 작성가이드 2절과 동일한
  요소 넘버링 규칙).
- 한 화면에 팝업이 여러 개면(등록/삭제/이메일공유 등) 각 팝업 페이지의 NO는 상위 화면
  Description에서 그 팝업을 설명한 영역 NO를 각각 따라간다(팝업마다 서로 다른 NO일 수 있음).
- screen-section id/파일 내 주석에도 상위 NO를 함께 적어(`<!-- popup for SCR-001 NO=7 -->`)
  나중에 상위-하위 매핑을 다시 찾기 쉽게 한다.
- **주의(2026-08-18 도입)**: 위 규칙은 팝업 하위 페이지 자체가 "요소 배지만 있고 자기 설명은
  없는" 얕은 페이지일 때를 전제로 한다. 만약 각 팝업 전용 페이지(`scr-001-popup-7-1` 등)가
  이미 자기 완결적으로 노출조건·입력조건·출력조건·인터랙션·예외Case·BE연동을 전부 갖추고
  있다면(즉 상위 NO의 설명을 그대로 반복하지 않고 그 팝업만의 상세를 담고 있다면), 상위 화면
  Description에 그 팝업들을 요약하는 NO 행("영역명: 팝업 영역")을 **별도로 또 만들 필요는
  없다** — 오히려 상위 요약 행과 하위 상세 페이지가 같은 내용을 다른 자리에서 반복하는
  중복이 된다(SCR-001 NO=7 "팝업 영역" 사고: `scr-001-cont-3` 페이지가 NO=7로 7-1/7-2/7-3
  팝업을 한 줄씩 요약했는데, 그 세 팝업은 각각 `scr-001-popup-7-1/7-2/7-3` 전용 페이지에서
  이미 완전한 설명을 담고 있어 순수 중복이었음). 새 팝업을 추가할 때는 먼저 "이 팝업들을
  요약하는 상위 NO 행이 정말 필요한가(하위 페이지가 아직 부실해서 상위에서 보완 설명이
  필요한가), 아니면 하위 페이지만으로 충분한가"를 판단하고 후자면 상위 요약 행을 만들지 않는다.
- **NO 행을 삭제할 때는 그 행이 속한 이어붙임(cont) 체인 전체를 함께 정리한다(2026-08-18
  사고 이력)**: 삭제 대상 NO가 어떤 cont 페이지의 유일한(또는 마지막) 내용이었다면, 그 NO 삭제로
  cont 페이지 자체가 빈 껍데기가 될 수 있다. 이 경우 ① 그 cont 페이지의 `screen-section` 전체를
  삭제하고 ② tab-nav의 해당 버튼(`showScreen('scr-NNN-cont-N', ...)`)도 함께 삭제하고 ③ 바로
  이전 cont 페이지가 그 삭제된 페이지를 향해 `<div class="desc-continue">다음 화면에 계속 ▼</div>`
  마커를 걸고 있었다면 그 마커도 제거한다(더 이상 이어지는 페이지가 없으므로). 세 가지 중
  하나라도 빠뜨리면 존재하지 않는 섹션을 가리키는 죽은 탭 버튼이 남거나, 실제로는 끝난 화면인데
  "다음 화면에 계속"이 표시되는 모순이 생긴다. 삭제 후 `check_dom_order`로 섹션 수가 정확히
  1 감소했는지, `grep`으로 삭제한 id 문자열이 tab-nav/본문 어디에도 남지 않았는지 반드시 확인.

- **`screen-section` 전체를 통째로 삭제할 때, Python 정규식으로 `<div\b|</div>` depth-tracking을
  직접 짜서 여는/닫는 태그 짝을 찾지 않는다(2026-08-19 사고 이력).** 최초 시도에서
  `tag_re = re.compile(r'<div\b|</div>')`로 매치한 뒤 `m.group().startswith('<div')` 분기로
  깊이를 세었는데, 정규식 자체가 `<div\b`(리터럴 백스페이스가 아니라 정규식 word-boundary
  이스케이프가 파이썬 문자열 안에서 깨짐)라서 `<div ...>` 형태의 실제 태그를 하나도 매치하지
  못하고 `</div>`만 매치했다. 그 결과 "여는 태그 depth+1, 닫는 태그 depth-1" 로직이 실제로는
  닫는 태그만 세는 카운터로 동작해, 삭제 대상 섹션의 **오프닝 `<div id="...">` 한 줄만 삭제되고
  내부 콘텐츠 전체(사이드바/카드그리드/Description 등 수천~2만자)가 파일에 그대로 남아
  다음 섹션 내용과 뒤섞이는 상태가 됐다(scr-012-cont-1 삭제 시도에서 738자만 지워짐 — 원래
  6000자 이상이어야 정상이었는데 이 크기 불일치로 즉시 발각). 다행히 `check_dom_order`로
  JS 에러는 안 잡혔지만(태그 자체는 여전히 balanced했음 — 단지 엉뚱한 위치에서 닫혔을 뿐)
  `git diff`로 실제 삭제된 줄을 눈으로 대조해서야 발견했다. **수정**: 섹션 전체 삭제는
  ① 먼저 `Grep`으로 `id="scr-NNN-cont-N"` 실제 라인 번호를 확인 → ② `Read`로 그 섹션의 시작
  직전 몇 줄과, 다음 형제 섹션(`<!-- ==== 다음 화면 주석 ==== -->`)이 시작되는 지점까지의 정확한
  1-indexed 라인 번호를 육안으로 확인 → ③ Python에서 `lines = f.readlines()`로 읽어
  `del lines[start_0idx:end_0idx]`처럼 **라인 번호 슬라이싱**으로 삭제한다(정규식 depth-tracking
  금지, `Edit` 도구의 텍스트 치환도 섹션이 수천 자짜리 한 줄일 때는 old_string이 너무 커서
  비현실적이므로 라인 슬라이싱이 유일한 안전한 방법). ④ 삭제 직후 `Read`로 삭제 지점 앞뒤를
  다시 열어 앞 섹션의 닫는 `</div>`와 다음 섹션의 여는 주석/`<div id=...>`가 자연스럽게
  이어지는지 육안 확인하고 ⑤ `check_dom_order`로 섹션 수가 정확히 1 감소했는지, `grep -c`로
  삭제한 id 문자열이 완전히 0건인지(부분 잔존 없음) 확인한다. **부가 교훈**: 이 사고가 만든
  손상 상태에서 `git stash`/`git checkout --`로 되돌리려 했으나, 되돌린 시점의 HEAD 커밋
  자체가 이미 이번 세션 초반 수정분을 일부 포함하고 있었다(온라인 세션과 로컬 세션이 병행
  작업 중인 리포지토리 특성 — CLAUDE.md의 "온라인 세션 ↔ 로컬 Claude Code 협업 워크플로"
  참고). 즉 `git checkout --`은 "세션 시작 시점"이 아니라 "가장 최근 커밋"으로 되돌리므로,
  이 파일을 다루는 세션은 작업 시작 전에 `git log --oneline -3 -- <파일>`로 HEAD가 실제로
  무엇을 담고 있는지 먼저 확인하는 습관을 들일 것 — "checkout하면 내가 만든 변경만 사라진다"고
  가정하지 않는다.

### Step 4-4. PDF/PPT 전용 정적 분할 페이지를 다시 한 페이지로 병합할 때 (2026-08-18 도입)

- 배경: 세로 스크롤(`scroll-wrap-detail` 등)이 있는 표는 HTML 화면에서는 스크롤로 전체 행을
  보여주지만, 정적 캡처인 PDF/PPT는 스크롤을 재현할 수 없다. 이를 해결하기 위해 표를
  PDF/PPT 전용 페이지(`.pdf-only-page`, `@media screen`에서만 숨김)로 별도 분리하는 패턴을
  쓰는데, 행 수가 페이지 예산을 넘으면 여러 페이지로 쪼개게 된다(예: SCR-001 "공정별 상세"
  17행을 6/7/4행 3페이지로 분할). 이후 사용자가 "한 페이지에 다 넣어달라"고 요청하면(예:
  17행 정도는 fit-to-page 축소(`applyPrintScaling`의 `zoom` 배율 조정)로 충분히 한 페이지에
  들어가는 경우), 분할 페이지들을 다시 하나로 병합해야 한다.
- **원칙: 손으로 텍스트를 복사/붙여넣기 하지 않는다.** 표 셀에 특수문자·한글·엔티티가 섞여
  있어 수작업 복사 시 인코딩이 깨지거나 일부 셀이 누락되기 쉽다. 대신 Python 정규식으로
  ① 각 분할 페이지의 `<div id="...">...개별 screen-section 전체</div>` 범위를 `<div\b`/`</div>`
  깊이 추적으로 정확히 찾고, ② 첫 페이지에서 `<tbody>(...)</tbody>` 안의 행들을 정규식으로
  뽑아 나머지 페이지의 행들을 순서대로 이어붙이고, ③ 첫 페이지의 id/상태 배지/우측 상단
  페이지 배지("표 1/3페이지" 등)를 "전체" 표현으로 바꾸고, ④ 나머지 페이지들의 섹션 전체를
  삭제한다. 병합 후 반드시 NO 값이 순서대로(1, 2, 3 ... 끝까지 결번 없이) 이어지는지
  정규식으로 재확인한다.
- **fit-to-page 축소를 믿고 페이지 표준 높이를 넘겨도 괜찮다.** 병합한 페이지의
  `.wireframe-wrap` 실제 높이가 이 문서의 다른 표준 페이지보다 커져도(예: 921px → 1204px),
  `applyPrintScaling()`이 각 섹션을 자신의 실제 `scrollWidth`/`scrollHeight`에 맞춰 개별
  `zoom` 배율로 축소하므로 PDF 페이지 수는 여전히 섹션 수와 일치한다(2026-08-18 SCR-001
  검증: 17행 병합 페이지가 다른 페이지보다 컸지만 PDF 50페이지=섹션 50개 그대로 일치).
  단, 검증(Step 9)에서 PDF 페이지 수 일치와 PPTX 텍스트 겹침(인디케이터 배지 외 비정상
  겹침 없음)은 반드시 재확인한다 — "커도 축소되니 괜찮다"는 가정 자체를 실측 없이
  신뢰하지 않는다.

### Step 5. 페이지 분할(오버플로우) 처리

- Description 내용이 와이어프레임 높이 예산을 넘으면(측정: `meta-box 높이 + wireframe 자연높이
  + 40px`vs`desc-table 실제 높이`) **청크 단위**로 이어붙임 페이지를 만든다.
- 청크 = 영역의 "인트로"(영역명+설명) 1개 + 요소별 1개씩. 절대 요소 중간을 임의로 자르지 않는다.
- **최우선 원칙: NO(영역) 하나는 가급적 한 페이지 안에서 통째로 유지한다.** 어떤 NO의 청크들이
  현재 페이지 예산에 다 들어간다면, 그 NO는 절대 페이지 중간에서 끊지 않는다 — 심지어 그 NO
  전체가 다음 NO와 함께 다음 페이지로 넘어가야 하는 상황이라도, "이번 페이지에 억지로 앞부분만
  채워 넣기"보다 "다음 NO는 그대로 다음 페이지로 통째로 넘기기"를 우선한다. 페이지 중간 분할은
  그 NO 하나의 청크 총량이 남은 예산은 물론 페이지 전체 예산조차 넘는(즉 한 페이지에 다 담을
  방법이 없는) 경우에만 허용하며, 그때도 반드시 청크(요소) 경계에서만 자른다(2026-08-18 사고
  이력: 1번 영역이 3개 요소 중 1-1/1-2만 페이지에 남고 1-3만 다음 페이지 맨 위에 뚝 떨어져
  분리됐고, 동시에 다 채워지지 않은 여유 공간에 2번 영역 인트로만 걸치듯 시작되는 두 가지
  문제가 함께 발생 — 원인은 페이지 예산 계산이 "남은 공간에 다음 청크가 들어가는가"만 보고
  그리디하게 채워서, NO 경계를 고려하지 않은 것. 수정: 픽셀 단위로 실측한 뒤 1번 영역의 4개
  청크를 모두 같은 페이지에 배치하고, 2번 영역은 그 페이지에 남는 공간만큼만(인트로+요소
  1~2개) 자연스럽게 이어 쓰고 나머지 요소부터 다음 페이지로 넘기는 방식으로 재작업했다.
  `paginate.py`의 `pack_pages()`를 쓸 때도 이 우선순위(NO 완결성 > 페이지 공간 최대 활용)가
  지켜지는지 결과물을 반드시 육안/스크린샷으로 재확인한다 — 알고리즘이 공간만 최적화하고
  NO 경계를 깨뜨리는 방향으로 청크를 나눌 수 있기 때문이다.
- **알고리즘 주의(중요 버그 이력)**: 그리디 패킹을 짤 때 "영역 경계 추적"과 "페이지 배분 결정"을
  한 번에 하면 청크가 조용히 유실될 수 있다(2026-08-13, 2026-08-14 두 세션에서 각각 발견/수정).
  반드시 ① 청크를 플랫 리스트로 먼저 배분 → ② 각 페이지 안에서 연속된 같은 영역번호를
  `itertools.groupby`로 재그룹 하는 2단계로 구현하고, **입력 청크 수 == 출력 청크 수**를
  `assert`로 검증한다(`scripts/paginate.py` 참고).
- 이어붙임 페이지는 원본과 동일한 와이어프레임+인디케이터를 반복하고, 이어지는 영역 행에는
  `class="cont-row"`(점선 상단 테두리)를 붙이며 NO는 원래 영역 번호를 그대로 반복한다(빈칸 아님).
- 원본 페이지 마지막에 `<div class="desc-continue">다음 화면에 계속 ▼</div>` 마커를 추가한다.

### Step 9. 최종 검증 (반드시 수행, 생략 금지)

1. `document.querySelectorAll('.screen-section')` 개수를 세어 예상 화면 수(원본 + 이어붙임
   페이지 + 부록 페이지)와 일치하는지 확인.
2. `page.on('pageerror', ...)`로 JS 에러가 없는지 확인.
3. PDF: `applyPrintScaling()` 경로로 headless Playwright `page.pdf()` 생성 후 PyMuPDF로 페이지
   수를 세어 **섹션 수와 정확히 일치**하는지 확인(불일치 시 대개 오버플로우로 인한 추가
   빈 페이지 — 어느 섹션인지 페이지별 텍스트를 추출해 찾아낸다).
4. PPTX: `downloadPPTX()` 버튼을 눌러 파일을 받고, `python-pptx`로 슬라이드 수 확인 + `zipfile`로
   풀어 모든 `ppt/slides/*.xml`이 `xml.dom.minidom`으로 파싱되는지 + `spAutoFit`이 0건인지(과거
   PowerPoint "복구" 손상의 근본 원인) 확인.
5. 대표 화면 몇 개(신규/관리자/이어붙임 페이지 포함)를 스크린샷으로 시각 확인.
6. **요소 인디케이터(`.indicator-el`)가 있는 화면은 세 렌더 폭 모두 확인**: Playwright에서
   `document.documentElement.style.width`/`document.body.style.width`를 `1240`(PDF)과
   `1680`(PPT)으로 각각 강제 설정 후 겹침(영역 vs 요소, 요소끼리) 및 음수좌표 여부를 재측정한다
   (기본 폭 상태도 포함해 최소 3회). 실제 다운로드한 PPTX를 열어 `python-pptx`로 도형 좌표(EMU)
   를 직접 대조하는 것이 가장 확실하다(HTML/PDF는 실브라우저 렌더라 문제가 잘 안 드러남 — 문제는
   주로 PPT의 커스텀 변환 로직에서 생김).
6-1. **팝업 페이지(`popup_page()`로 만든 화면)는 PPTX 도형 좌표로 배경-모달 텍스트 겹침을 별도
   검사한다(2026-08-18 도입, 생략 금지)**: `downloadPPTX()`를 실행해 받은 PPTX를
   `python-pptx`로 열어, 각 슬라이드의 텍스트 도형 쌍을 좌표로 겹침 비율을 계산한다(인디케이터
   배지·"▼ 스크롤" 같은 의도된 오버레이 배지는 제외). 15% 이상 겹치는 쌍이 있으면 대개
   `.popup-backdrop` 마커 누락이 원인이다(위 Step 3 문단 참고) — HTML/PDF 스크린샷만으로는
   이 문제가 전혀 드러나지 않으므로 팝업 페이지가 있는 문서는 이 검사를 빼먹지 않는다.
7. **실 프론트 캡처와 최종 대조(2026-08-15 도입, 생략 금지)**: 손그림 와이어프레임이 실제
   구현의 UI 디자인(테두리/음영/여백/색상 배치 등 구조적 특징)을 놓치지 않았는지, 로컬
   `src/frontend`를 Playwright로 띄워 화면별로 실제 스크린샷을 찍고 나란히 비교한다. 픽셀
   단위로 똑같아야 하는 건 아니지만(이 문서는 의도적으로 저충실도 손그림 스타일), **다음
   구조적 요소는 와이어프레임에도 반드시 나타나야 한다**: (a) 카드형 컨테이너(외곽 테두리+
   그림자)가 있는 영역은 와이어프레임에도 테두리 박스로 표현, (b) 여러 개의 하위 테이블/패널이
   같은 화면에 나란히 있으면 그 구획이 와이어프레임에도 분리돼 보이는지, (c) 스크롤 가능
   영역(Step 4-1)이 표시돼 있는지, (d) 헤더 행 음영이나 강조 색상이 있는 셀(BP 라인 등)이
   와이어프레임에도 구분돼 보이는지, (e) **카드/그리드 요소가 실제 CSS에서 컨테이너 폭에 비례해
   꽉 채우는 배치(`display:grid; grid-template-columns:repeat(N,1fr)` 등)인지, 아니면 고정
   픽셀 폭으로 좌측 정렬되고 남는 여백이 있는 배치(`flex-wrap:wrap`+고정 `width`)인지 — 실제
   `common.css`의 해당 클래스 정의를 읽고 그대로 재현한다(2026-08-19 사고: MTRM-MAIN "생산기술
   Tech PR" 카드가 실제로는 `.card-grid-3`(`grid-template-columns:repeat(3,1fr)`)로 패널 폭을
   정확히 3등분해 꽉 채우는데, 와이어프레임은 `flex; flex-wrap:wrap`에 카드 `width:120px`
   고정값을 줘서 카드가 작게 좌측에 몰리고 우측에 큰 여백이 남는 형태로 그려짐 — 사용자가 두
   차례에 걸쳐 지적한 뒤에야 발견. 처음엔 썸네일 종횡비(16:9→1:1)만 고치고 이 배치 방식 차이를
   놓쳤다). 카드 개수가 고정(N개)이고 그리드로 폭을 나눠 채우는 컴포넌트는 와이어프레임에서도
   폭을 하드코딩하지 않고 `display:grid; grid-template-columns:repeat(N,1fr)`로 동일하게
   구현한다 — "저충실도 손그림 스타일"은 색상·질감·디테일을 단순화하라는 것이지, 레이아웃의
   배치 방식(고정폭 vs 비율분할)까지 임의로 바꿔도 된다는 뜻이 아니다.
   대조 결과 빠진 게 있으면 그 자리에서 보완하고, 스크린샷
   자체는 검증용 산출물이므로 커밋 전에 정리한다(스크립트/이미지 모두 scratchpad 사용 권장).

## 1-1. 재발 방지 체크리스트 (2026-08-18 도입, 작업 종료 전 필수)

이 문서를 다루면서 실제로 사용자에게 지적받았던 사고 유형을 `verify.py`의 함수로 코드화했다.
**"가이드에 적어뒀으니 사람이 기억해서 피하겠지"에 의존하지 않는다** — 이 문서를 수정한 뒤에는
반드시 아래 순서로 기계적으로 돌려서 확인하고, 결과를 보고에 포함한다. 특정 사고 유형이
가이드 문서 다른 절(Step 3/4/5)에 서술돼 있어도, 실제 재발 방지는 이 체크리스트 실행이 한다 —
서술은 "왜"를 설명할 뿐 "확인했는가"를 보장하지 않는다.

**R17 관련 특별 주의(2026-08-19 도입)**: `check_all_regressions()`를 돌리면 R17("카드 그리드
고정폭 의심")이 자동으로 함께 실행되지만, R12/R15와 마찬가지로 **정보성 체크라 `ok` 판정에
포함되지 않는다** — R17이 0건이라고 해서 "카드/그리드 배치가 실제 CSS와 일치한다"가 자동으로
보장되는 게 아니다(R17은 `flex-wrap:wrap`+동일 `width:NNpx` 반복이라는 특정 잘못된 패턴만
탐지하며, 그 패턴으로 안 걸리는 다른 형태의 배치 방식 불일치는 못 잡는다). 카드/그리드형
컴포넌트를 새로 그리거나 수정할 때는 R17 결과와 무관하게 Step 9-(e)에 따라 **실제
`common.css`의 해당 클래스(`display:grid` vs `flex`, `grid-template-columns` 비율)를 직접
읽고 대조하는 절차를 생략하지 않는다.** R17이 의심 항목을 보고하면, 그 컴포넌트가 실제로도
개수 가변적 목록(고정폭이 자연스러움, 예: 첨부파일 카드)인지 아니면 고정 개수 그리드(비율분할이
맞음, 예: MTRM-MAIN Tech PR 3장)인지 실제 구현 근거로 사람이 판단한다 — 무조건 grid로
바꾸는 것도, 무조건 통과시키는 것도 아니다.

**R18 관련 특별 주의(2026-08-19 도입)**: R17이 그리드 컨테이너 자체의 배치 방식(고정폭 vs
비율분할)을 본다면, R18은 그리드 배치는 맞는데 **카드 내부 썸네일의 종횡비**가 실제 CSS와
다른 경우를 잡는다(사고 사례: SCR-014 "기술동향 - 수정 선택모드"가 일반 목록뷰(scr-014)와
동일한 `grid-template-columns:repeat(5,1fr)`를 썼는데도 썸네일만 `height:110px` 고정값으로
그려져, 실제 `.media-thumb`의 `aspect-ratio:1/1`보다 카드가 훨씬 납작하게 나왔다 — 같은
SCR-014 화면 안에서도 일반 모드는 이미 정확했고 선택모드만 어긋나 있었다). **같은 화면의
다른 상태(선택모드/상세뷰/팝업 등) 페이지를 새로 만들거나 수정할 때, 이미 확인한 상태 페이지의
구현을 그대로 복사한 것이 아니라면 그 페이지도 별도로 실제 CSS와 대조한다** — "이 화면은 이미
확인했다"는 화면 단위 판단이지 상태 단위 판단이 아니다. R17과 마찬가지로 정보성이라 `ok`
판정에는 포함되지 않으며, 의심 항목이 나오면 `src/frontend/css/common.css`의 실제 썸네일
클래스 정의를 직접 읽고 판단한다.

  게 아니라, 원본 화면 자체도 표준 페이지 zoom 배율이 텍스트를 읽을 수 없게 만들 정도로
  콘텐츠가 많으면 원본 표 데이터 자체를 1페이지 분량으로 줄이고 전체 데이터는 PDF/PPT 전용
  페이지에서만 제공하는 쪽을 우선한다). 이 문서의 기존 아키텍처(오버플로우를 실행 시점 동적
  계산이 아니라 미리 계산해 정적 HTML로 박아넣는 방식, Step 5)와 일관되게, PDF/PPT 전용
  정적 섹션을 원본 화면 바로 뒤에 추가하고 `@media screen`으로 HTML에서는 숨긴다(R9와 동일한
  매체 분기 기법). 행 분할 개수는 Playwright로 헤더 높이 + 행별 실제 렌더 높이를 실측해
  페이지 예산에 그리디 패킹한다(재사용 헬퍼: `screens_common.py`의
  `paginate_table_rows(row_heights, page_budget, header_height)`). 새로 추가한 섹션도
  `.screen-section`이므로 `check_pdf_page_count`/`check_pptx_integrity`의 기대 슬라이드 수에
  자동 포함된다 — 섹션을 추가했다면 그 즉시 이 두 카운트가 늘어난 새 값으로 검증해야 한다.
  PDF/PPT 전용 페이지는 사이드바/탭/필터 등 그 페이지의 존재 이유가 아닌 영역을 제거하고
  표만 남기는 것이 원칙이다(R8 참고).
- **R11. 필터바 등 실제 컴포넌트 옵션(hideLabels 등)을 놓침(2026-08-19, SCR-001)**: `render.js`의
  `renderFilterBar(labels, opts)`처럼 컴포넌트 함수가 옵션 인자(`hideLabels`, `noReset` 등)에
  따라 렌더 결과가 달라지는 경우, `data.js`의 필터명 배열만 보고 "라벨이 당연히 있겠지"라고
  넘겨짚어 실제로는 라벨이 렌더링되지 않는 필드에 라벨을 그려 넣는 사고가 났다(SCR-001 필터바
  5종에 실제로는 없는 "제품군/제품/지역/공장/라인" 라벨 텍스트를 추가해뒀던 것). **확인 방법**:
  렌더 함수 호출부(`render.js`에서 그 화면의 렌더 함수 안, 예 `renderFilterBar(D.scr001Filters, {...})`)의
  **옵션 객체 전체**를 반드시 읽고, `hideLabels`/`noReset`/`syncBadge` 등 조건부 렌더링에 영향을
  주는 옵션이 있는지 확인한 뒤에 와이어프레임 구조를 결정한다 — 함수의 데이터 배열(`labels`)만
  보고 판단하지 않는다. 부수 효과 주의: 라벨 한 줄을 추가/제거하면 그 아래 모든 요소의 세로
  좌표가 밀리므로, 고정 픽셀로 실측해둔 인디케이터(`.indicator`/`.indicator-el`) 좌표도 반드시
  함께 재실측한다(R3와 연계).

**R12. R6(Description 빈공간 과다)과 R7(PDF 축소배율 붕괴)이 서로 다른 렌더 폭을 기준으로
측정해 상충하는 사례(2026-08-19, SCR-001 cont-1)**: R6은 Playwright의 현재 뷰포트 폭(임의
폭, 이 문서는 보통 1800px)에서 `.desc-wrap` 높이를 재고, R7은 PDF 페이지 폭(약 1240px)으로
`body.style.width`를 강제한 뒤 섹션 전체 `scrollHeight`를 잰다. 두 체크가 서로 다른 폭에서
측정하다 보니, R6이 "이 페이지 여백이 크니 다음 청크를 채워라"라고 지적한 대로 페이지 분할을
다시 짰다가 오히려 R7을 터뜨리는 사고가 났다: SCR-001의 이어붙임 2페이지 구성(원래 cont-1=NO4만,
cont-2=NO5+NO6)에서 cont-1의 R6 slack(HTML 폭 기준 376~438px)을 줄이려고 NO=5를 cont-1로
옮겨(cont-1=NO4+NO5, cont-2=NO6만) HTML 폭에서 재측정했더니 R6 문제가 해소된 것처럼 보였다.
그런데 실제 PDF 렌더 폭(1240px)에서는 `.desc-wrap`도 76:24 비율에 따라 약 298px로 좁아지므로
NO=4+NO=5 텍스트가 훨씬 많은 줄바꿈을 먹어 `.desc-wrap` 높이가 1335px까지 치솟았고, 그 결과
섹션 전체 `scrollHeight`가 1416px까지 커져 `applyPrintScaling()` 배율이 0.479(R7 기준 0.55
미만)로 붕괴했다 — 즉 HTML 뷰에서는 "여백이 줄어든 개선"으로 보였지만 PDF/PPT 결과물은
텍스트가 읽을 수 없이 깨지는 퇴행이었다. **원인 진단**: `paginate.py`의 `measure_budget`/
`measure_chunks`로 페이지 분할을 재계산할 때 HTML 기본 뷰포트 폭에서만 측정하고 PDF 렌더 폭
(`body.style.width`를 페이지 폭으로 강제한 상태)에서 재측정하지 않았다. **해결**: PDF 폭
기준으로 NO별 실제 렌더 높이를 다시 재서(NO4=539px, NO5=611px, 가용 공간 1045px) NO4+NO5가
합쳐서 1150px로 페이지 예산을 초과함을 확인했고, Step 5 "NO 완결성 최우선" 원칙에 따라 NO=5를
분할하지 않고 원래 배치(cont-1=NO4만, cont-2=NO5+NO6)로 되돌렸다 — cont-1의 여백(PDF 폭 기준
약 306px)은 "NO4 하나만 페이지를 채우는" 불가피한 결과로 확정했다(다음 청크를 더 넣을 방법이
없다는 뜻이지, 페이지 분할 로직의 결함이 아니다). **재발 방지**: R6이 지적한 여백을 채우려고
청크를 재배치할 때는 반드시 (a) PDF 렌더 폭(`body.style.width`를 페이지 폭으로 강제)에서 NO별
높이를 재측정하고, (b) 재배치 후 R7(`check_print_scale_collapse`)을 다시 돌려 붕괴가 없는지
확인한다 — HTML 폭 기준 R6 결과만 보고 "여백이 줄었으니 성공"이라 판단하지 않는다. 이 대조
과정을 `verify.py`의 `check_desc_underflow_pdfwidth`(R12)로 코드화했다: R6과 동일한 대상
선정 기준으로 PDF 렌더 폭에서 slack을 다시 재고, 그래도 여전히 크면 "R7과 대조해 불가피한
여백인지 확인하라"는 note를 함께 반환한다(둘 다 자동으로 정답을 내지 못하므로 `ok` 판정에는
포함하지 않는 정보성 체크 — R6/R7을 사람이 함께 대조하는 것을 대체하지 않는다).

**R14. `.pdf-only-page`의 반대 방향 매체 분기(`.screen-only-page`) 도입 시 CSS 특정도 함정
(2026-08-19, SCR-001 `scr-001-scroll`)**: "PDF/PPT는 스크롤이 재현 안 되니 정적 분할 페이지가
필요하다"(R8/R10)는 결정으로 원본 화면의 "공정별 상세" 표를 1페이지 분량으로 줄였더니, 그
여파로 **HTML 브라우저에서 표 전체를 스크롤로 보던 화면 자체가 사라지는** 사고가 발생했다
(사용자 지적: "html 3~4p는 스크롤 기능이 있었는데 지금 없어졌잖아"). 해결책은 원본과 동일한
캔버스에 17행 전체+스크롤 wrap을 담은 새 섹션(`scr-001-scroll`)을 추가하되, 이 섹션 자체는
**PDF/PPT에서는 제외**해야 했다(안 그러면 R7 텍스트 깨짐 사고가 새 섹션에서 재발). `.pdf-only-page`
(`@media screen`에서 숨김)의 정반대인 `.screen-only-page`(`@media print`에서 숨김) 클래스를
처음 CSS만으로 시도했으나, 이 문서의 기존 규칙 `.screen-section:not(#cover-page) { display:grid
!important; }`의 `:not()` 셀렉터 안에 있는 `#cover-page`라는 **ID**가 그 규칙 전체의 특정도를
ID 수준으로 끌어올려서, 클래스 셀렉터(`.screen-only-page`)로는 특정도 싸움에서 이길 수 없었다
(실측: `getComputedStyle()`로 `display:grid`가 그대로 이김을 확인). **해결**: 섹션 자신의
`#id.screen-only-page` 형태로 ID를 셀렉터에 포함시켜 특정도를 맞췄다. PPTX는 `downloadPPTX()`가
브라우저 `@media` 상태를 아예 거치지 않고 라이브 DOM을 순회하므로, CSS 규칙과 별개로 그 함수의
슬라이드 생성 루프에도 `.screen-only-page`면 `continue`하는 가드를 추가해야 했다(R9가 반대
방향에서 이미 겪은 것과 동일한 매커니즘). 이 전체 검증을 `check_screen_only_page_hidden_in_print`
(R14a, print 미디어에서 실제 `display:none`인지 실측)와 `check_screen_only_page_pptx_skip`
(R14b, `downloadPPTX()` 소스에 continue 가드가 존재하는지 정적 확인)로 코드화했다. **재발
방지**: 앞으로 "HTML 전용, PDF/PPT 제외" 페이지를 새로 만들 때는 반드시 `#id.screen-only-page`
형태로 ID를 셀렉터에 포함시키고, `downloadPPTX()` 루프에 continue 가드를 추가한 뒤 R14a/R14b로
실측 검증한다 — "클래스만 붙이면 되겠지"라고 넘겨짚지 않는다.

**R14 후속: PDF/PPTX 기대 페이지수는 `dom["count"]`가 아니라 `dom["pdf_expected_count"]`를 쓴다
(2026-08-19 SCR-002 세션에서 오탐 발견 및 수정)**: `.screen-only-page` 섹션(scr-001-scroll)은
`.screen-section` 개수(`dom["count"]`, 이 문서 기준 51)에는 포함되지만 PDF/PPTX에는 나타나지
않으므로, `check_pdf_page_count(expected_sections=dom["count"])`처럼 그대로 넘기면 실제로는
정상인 PDF(50페이지)가 "1장 부족"으로 상시 오탐 처리된다. `check_dom_order`가 반환하는
`screen_only_count`/`pdf_expected_count`(= count - screen_only_count)를 이용해
`expected_sections=dom["pdf_expected_count"]`로 검증할 것 — `.pdf-only-page`(scr-001-table/
table-2)는 반대로 HTML에서만 숨겨질 뿐 PDF에는 그대로 나오므로 count에서 뺄 필요가 없다.

**R6/R12 판단 시 주의(2026-08-19 SCR-002 세션 확인 사례, scr-004/scr-012/scr-014)**: R6(HTML
뷰 폭 기준 여백)이 100px 이상 여백을 잡아도, R12(PDF 렌더 폭 기준 재측정)에서 문제로 잡히지
않으면 대개 실제 결함이 아니다 — HTML 뷰는 폭이 넓어 Description 텍스트 줄바꿈이 적지만, PDF
폭(~1240px)에서는 같은 텍스트가 더 많이 줄바꿈되어 desc-wrap 높이가 늘어나며 여백이 자연히
줄어든다. 위 세 화면은 R6만 걸리고 R12는 통과했으므로 페이지를 다시 짜지 않고 그대로 두는 것이
맞는 판단이었다(대조군: scr-001-cont-1은 R6·R12 둘 다 걸려 "NO4 하나만 페이지를 채우는 불가피한
결과"로 이미 확정된 별도 사례 — 위 488행 문단 참고). R6 단독 결과만 보고 페이지를 합치려 들지
말고 반드시 R12와 대조할 것.

**R15. NO 번호가 같은 그룹 내 두 섹션에서 서로 다른 내용을 가리키며 충돌(2026-08-19,
`scr-001-scroll` vs `scr-001-cont-1` NO=4)**: R14로 새로 만든 `scr-001-scroll`("공정별 상세
전체 보기" 페이지)의 Description에 "요소·조건 상세 설명은 원본 화면 NO=4를 참고"라는 짧은
안내문을 NO=4로 붙였는데, 같은 화면 그룹의 `scr-001-cont-1`에도 진짜 "상세 영역" 설명이 NO=4로
이미 존재해서, 같은 번호가 서로 다른 두 페이지에서 서로 다른 내용을 가리키는 충돌이 생겼다
(사용자 지적: "NO4 상세설명 텍스트 노출 영역이 2화면으로 나눠져 있던데??"). **표준 해결
절차(다음에 유사 사고가 나면 그대로 적용)**:
1. 두 섹션 중 어느 쪽이 "진짜 상세설명"이고 어느 쪽이 "다른 페이지를 참고하라"는 안내문/요약인지
   판별한다(안내문 쪽은 보통 텍스트가 짧고 "참고", "확인 가능합니다" 같은 리다이렉트 표현을
   포함한다).
2. 안내문 쪽 섹션의 Description `<td class="num">N</td>`을 `<td class="num">-</td>`로 바꿔
   번호를 뗀다 — 그 섹션 안의 안내 정보(무엇을 어디서 볼 수 있는지)는 그대로 남기되, "이것도
   NO=N의 정식 설명이다"라는 오해만 없앤다.
3. 그 섹션의 캔버스에 있던 대응 `.indicator`(영역 배지, N번)도 함께 제거한다 — Description
   번호와 캔버스 배지는 1:1 대응이 원칙이므로, 번호만 떼고 배지를 남기면 그 배지가 무엇을
   가리키는지 알 수 없는 새 혼란이 생긴다.
4. 진짜 상세설명 쪽 섹션은 그대로 둔다 — 그 쪽이 그룹 내 유일한 정식 NO=N이 된다.
5. 어느 쪽을 안내문으로/정식 설명으로 남길지, 배지도 함께 지울지는 AskUserQuestion으로 사용자
   확인 후 진행한다(자동 판단하지 않는다 — 어느 페이지가 더 자연스러운 기준점인지는 문서 맥락에
   따라 다르다).

이 탐지를 `check_no_number_ambiguity`(R15)로 코드화했다: 같은 화면 그룹 안에서 같은 NO가
서로 다른 영역명(`<b>` 텍스트)으로 두 섹션 이상에 등장하면 잡아낸다. **오탐 수정 이력(같은
날 발견)**: 초판 구현은 팝업 섹션까지 포함해 비교했다가 SCR-001/002/004/006/007/008/009/
010/011/012/014 전 그룹에서 대량 오탐이 났다 — 팝업은 Step 4-2 규칙상 상위 NO를 이어받거나
자기 완결적이면 독자적으로 새로 매기는 것 둘 다 정상이라, "팝업 NO=1 vs 상위 화면 NO=1"이
우연히 겹쳐도 충돌이 아니다. `.popup-backdrop` 마커(R6/R7과 동일 판별 방식)로 팝업 섹션을
비교 대상에서 제외해 해결했다. 또한 `cont-row`(Step 5 정상 이어붙임 반복 행)도 `<b>` 텍스트가
보통 "영역명:"이 아니라 세부 요소 라벨("요소: 2-2 수정" 등)을 담고 있어 원본 행과 문자열이
달라 오탐이 났다 — `cont-row` 클래스가 있는 행도 비교 대상에서 제외했다. 정보성 체크(`ok`
판정 미포함)이므로, 이 함수가 뭔가를 잡아내면 반드시 사람이 위 표준 해결 절차를 적용해
판단한다 — 자동으로 고치지 않는다. 참고: 검증 과정에서 `scr-014-selectmode`(선택모드 전환
화면)가 기저 화면 `scr-014`와 같은 NO=1/2를 서로 다른 내용으로 쓰는 것도 발견됐는데, 이는
팝업도 cont-row도 아닌 제3의 페이지 변형 유형이라 이 문서에 아직 명시적 작성 관례가 없다 —
`-selectmode`류 변형 페이지의 NO 넘버링 규칙을 앞으로 정리하고, 정리되면 R15의 제외 조건에도
반영할 것(당장은 그대로 정보성 결과에 남겨 사람이 인지하게 둔다).

**R20. `downloadPPTX()`의 desc-table 8pt 재계산이 원본에 없는 가상 이월 페이지를 만듦
(2026-08-25, SCR-014)**: 사용자가 첨부한 "수정된 샘플" PDF(48페이지)를 기준으로 `downloadPPTX()`
결과 PPTX를 검증했는데 49페이지가 나와 1장 차이가 있었다. 원인은 desc-table을 PPT 전용 8pt
폰트로 재계산하는 `sbpptxBuildDescTable()`의 구조적 특성 — 캔버스 전체는 `scale`(HTML→슬라이드
축소 배율, 이 문서 기준 약 71%)만큼 폭이 줄어드는데 desc-table 폰트는 8pt로 고정되다 보니,
폭 축소율과 폰트 축소율이 어긋나 상대적으로 텍스트가 더 많은 줄을 차지하게 된다. SCR-014는
원본 HTML(12px 기준)에서는 Description NO=1~3이 여유 있게 한 페이지에 들어가 `-cont-1` 청크가
애초에 없었는데, PPT 8pt 재계산에서는 NO=3 행이 캔버스 높이를 약 0.4in 초과한다고 판정됐다.
`downloadPPTX()`의 자동 이월 로직(6993행 근처 주석 "자동 이월(2026-08-24 사용자 요청)" 참고)은
이런 경우 원본에 없는 `-cont-N` 섹션을 **화면 전체(사이드바·GNB·필터·카드 그리드 전부)를
`cloneNode(true)`로 복제해서** 즉석에서 만들어 이어붙이는데, 이번 사고는 그 오버플로우 판정
자체가 육안상 전혀 넘치지 않는 근소한 경계 케이스(0.4in)였다는 게 문제였다 — 실제로 렌더링해
보면 두 페이지(원본 SCR-014와 가상 `-cont-1`) 캔버스가 거의 완전히 같아 보여서, 육안 대조만으로는
"왜 같은 화면이 두 번 나오지?"라는 의문 없이 "일치한다"고 잘못 판단하기 쉬웠다(실제로 이 세션의
1차 검증에서 이 오탐을 놓치고 "완전히 일치"라고 잘못 보고한 이력이 있다 — 페이지 수 자체를
반드시 먼저 비교할 것).

**해결**: `sbpptxBuildDescTable()`의 행 단위 오버플로우 판정 직후, 초과분이 작으면(기본
`SMALL_OVERFLOW_TOLERANCE_IN = 0.5`in 이하) 새 이월 페이지를 만들지 않고 그 표에 그대로 담아
캔버스 하단 여백을 소폭 침범하는 쪽을 택하도록 조기 분기를 추가했다 — 페이지가 통째로 하나 더
늘어나는 것보다 훨씬 덜 눈에 띄는 트레이드오프로 판단(AskUserQuestion으로 사용자에게 확인 후
진행). 이 함수는 desc-table을 쓰는 모든 화면에 공통 적용되므로, 다른 화면에서 이미 정당한
이월(원본에 `-cont-N`이 실제로 존재하는 케이스)까지 이 조기 분기가 삼켜버리지 않는지 주의—
`SMALL_OVERFLOW_TOLERANCE_IN`을 무작정 키우면 진짜 넘치는 텍스트도 그냥 캔버스 밖으로 삐져나온
채 방치될 수 있으므로, 이 상수를 바꿀 때는 R20으로 전 화면을 다시 스캔해 새로 `within_tolerance:
false`가 되는 화면이 없는지 확인할 것.

**재발 방지**: 이 판정 로직 자체를 `check_pptx_phantom_overflow_pages`(R20)로 코드화했다 —
`downloadPPTX()`를 실제로 실행/다운로드하지 않고도, 각 원본 SCR 섹션(팝업·이미 존재하는
`-cont-N` 제외)에 대해 `sbpptxBuildDescTable()`을 직접 호출해 `hasOverflow`를 실측하고, 원본
HTML에 그 화면의 `-cont-1` 섹션이 실제로 없는데도 오버플로우가 난 경우만 걸러 초과분(in)을
함께 보고한다. 초과분이 `SMALL_OVERFLOW_TOLERANCE_IN`(기본 0.5in, `downloadPPTX()`의 실제
상수값과 반드시 동기화할 것 — 두 값이 어긋나면 R20이 실제 다운로드 결과와 다른 기준으로
판정하게 된다) 이하면 `downloadPPTX()`가 이미 처리하므로 정상, 초과하면 새 가상 페이지가
생길 것이므로 결함으로 분류한다. **다만 이 R20 정적 체크는 desc-table 계산 로직만 재현할
뿐, 실제 다운로드한 PPTX의 슬라이드 수와 완전히 같은 보증은 아니다 — 결정적 검증은 항상
`check_pptx_integrity(expected_slides=dom["pdf_expected_count"])`로, 실제로 다운로드한
PPTX 파일의 슬라이드 수를 세는 것이다.** R20은 그 최종 검증에서 실패가 나기 전에 원인을
미리 좁혀 찾기 위한 보조 진단 도구로 쓴다.

**R24. desc-table pull-forward — "다음 화면에 계속" 배너 위 여백을 다음 화면 내용으로 채움
(2026-08-25 도입)**: 원본 HTML은 각 `-cont-N` 화면마다 어떤 Description NO를 담을지 사람이
미리 손으로 배정해 둔다(예: SCR-001은 `scr-001`=NO1~3, `cont-1`=NO3~4, `cont-2`=NO5~6).
PPT 변환 시 desc-table이 그 배정된 NO만 그리고 나면, 텍스트 분량이 짧은 화면일수록 캔버스
하단(배너 고정 위치)까지 큰 공백이 남는다 — 배너 자체는 이미 항상 캔버스 하단 고정
위치(`wfBottomIn - bannerReserveIn`)라 위치 문제가 아니라, "표 내용이 배정된 만큼만 그려지고
멈춘다"는 게 근본 원인이다(사용자가 "2p는 배너 위 공백이 거의 없는데 3p는 왜 큰가" 질문을
계기로 발견).

**요청 사항**: 영역(NO)이나 요소 단위가 아니라 **줄 단위**로 잘라서, 다음 화면 desc-table의
앞부분을 끌어와서라도 배너 직전까지 항상 꽉 채우고, 잘린 나머지만 다음 페이지 상단에서
이어지게 한다. 원본 HTML의 캔버스(와이어프레임 이미지/표)는 그대로 두고 PPT의 desc-table
콘텐츠 배분에만 적용한다 — 그 결과 같은 페이지 안에 서로 다른 NO의 설명이 상단/하단에 걸쳐
보일 수 있는데(예: cont-1 페이지 하단에 cont-2의 NO=5 앞부분이 먼저 나옴), 사용자가 이
트레이드오프를 명시적으로 승인했다.

**구현 위치**(`downloadPPTX()` 내부, `sbpptxBuildDescTable` 및 그 헬퍼):
- `sbpptxParseDescTableBodyRows(table)`: desc-table의 본문 행(NO/상세설명)만 좌표 계산 없이
  순수 데이터로 파싱하는 헬퍼. pull-forward가 "다음 섹션의 desc-table"을 미리 읽어야 해서
  기존 파싱 로직에서 분리했다.
- `downloadPPTX()`의 섹션 순회 루프에서, 각 섹션 처리 전에 `sections[i+1]`이 같은 화면 그룹의
  다음 `-cont-N` 청크(팝업 아님)인지 확인하고 맞으면 그 desc-table을 `sbpptxParseDescTableBodyRows`로
  미리 파싱해 `pullCandidateRows`로 준비해 둔다.
- `sbpptxBuildDescTable(..., pullForwardRows, pullForwardSkipCount)`: 시그니처에 두 인자가
  추가됐다. 자기 표의 원본 NO 행을 다 그리고도 `maxHeightIn` 여유가 남으면(표가 오버플로우로
  조기 리턴하지 않고 끝까지 도달한 경우에만) `pullForwardRows`를 순서대로 채운다 — 완전히
  들어가면 그대로, 마지막 항목이 넘치면 `sbpptxSplitRunsAtLine`으로 줄 단위로 잘라 앞부분만
  채우고 나머지는 반환값 `pulledPartialAfterRuns`에 담는다. 몇 개 항목을 완전히 끌어왔는지는
  `pulledCount`에 담긴다.
- `downloadPPTX()`는 `built.pulledCount`/`built.pulledPartialAfterRuns`가 있으면
  `pendingPullForward = { fromId: sectionBaseId, count, partialAfterRuns }`로 기록해 뒀다가,
  **다음** 섹션 처리 시(`myPullForwardSkip`) 그 화면 그룹이 일치하면 사용한다 — 잘린 나머지는
  `effectiveQueue`(기존 오버플로우 이월 큐와 동일한 `prependQueue` 조립 경로)에 앞줄로 붙이고,
  완전히 끌려간 개수(`pullForwardSkipCount`)는 `sbpptxBuildDescTable` 내부에서 자기
  `bodyRowDefs.splice(0, pullForwardSkipCount)`로 제거해 중복 렌더링을 막는다.
- 기존 `pendingOverflowQueue`(표가 넘쳐서 다음 화면으로 미는 이월)와 새 `pendingPullForward`
  (표가 남아서 다음 화면 것을 당겨오는 것)는 방향이 정반대이지만 동시에 발생하지 않는다
  (넘칠 때는 당길 필요가 없고, 남을 때는 넘칠 게 없다) — 두 상태 변수는 독립적으로 유지된다.
- "다음 화면에 계속" 배너 노출 조건 자체는 바꾸지 않는다 — pull-forward는 배너 위 공백을
  메울 뿐, 다음 화면에 아직 내용이 남아있는 한(원본 HTML에 `-cont-N` 청크가 실제로 있는 한)
  배너는 그대로 유지된다.

**검증**: SCR-001(2~4p)과 SCR-006(23~24p)에서 pull-forward가 배너 위 공백을 채우고 다음
페이지가 이어지는 지점부터 정상 시작하는 것을 실측 확인(스크린샷 대조), 48슬라이드 유지,
PPTX 무결성(XML 손상 0건, spAutoFit 0건) 통과, `check_all_regressions` R1~R22 회귀 없음
확인. **자동 검증 함수는 이번 세션에서 코드화하지 않았다** — 다음에 이 문서를 여는 세션은
새 화면/새 -cont-N 청크를 추가하거나 desc-table 관련 로직을 다시 만질 때, pull-forward가
의도대로 동작하는지(배너 위 공백이 없는지, 다음 페이지 시작점이 잘리지 않고 이어지는지)
반드시 스크린샷으로 직접 확인할 것 — `check_all_regressions`가 이 사고 유형을 자동으로
잡아주지 않는다.

**R25. SMALL_OVERFLOW_TOLERANCE_IN과 배너 겹침** — 이 허용치는 원래 `-cont-N`이 없는 화면
(SCR-014류)이 8pt 재계산 시 근소 초과로 가상 이월 페이지가 생기는 것을 막으려고 도입됐다.
그런데 `-cont-N`이 실제로 있는 화면(SCR-003류)에서도 무조건 적용되다 보니, 표 마지막 행이
배너 예약 공간(`maxHeightIn`)을 살짝 넘겨도 그대로 그려져 "다음 화면에 계속" 배너와 겹쳐
보이는 문제가 생겼다. 해결: `sbpptxBuildDescTable`에 `hasRealNextChunk` 인자를 추가하고,
호출부(`downloadPPTX()`)에서 이미 계산돼 있던 `nextIsSameChainCont`를 그대로 전달한다.
`hasRealNextChunk === true`(다음 섹션이 실제 `-cont-N`)면 허용치를 건너뛰고 정상 이월시켜
pull-forward(R24)가 다음 페이지 맨 위에 자연스럽게 이어 붙이게 하고, `false`(SCR-014류처럼
받아줄 다음 페이지가 없음)일 때만 기존 허용치를 유지해 가상 페이지 생성을 막는다. 검증:
SCR-003(14~15p)에서 "결과 조회." 텍스트가 15p로 정상 이월되고 배너와 안 겹침, SCR-014는
여전히 5페이지(가상 페이지 재발 없음), 전체 48슬라이드·PPTX 무결성(zip/spAutoFit 0건) 통과
확인(2026-08-25). 자동 검증 함수는 코드화하지 않음 — desc-table 관련 로직을 다시 만질 때는
SCR-003류(실제 다음 페이지 있음)와 SCR-014류(없음) 둘 다 스크린샷/텍스트 추출로 직접 확인할 것.

  `paginate_table_rows`(표 행을 실측 높이로 그리디 패킹, R10 참고)가 추가됨 — 새 팝업/요소
  배지/표 분할은 이 헬퍼들을 우선 재사용한다.
- `desc_common.py` — Description 표 생성기(정책 반영)
- `paginate.py` — Description 청크 측정 + 안전한 2단계 그리디 패킹(버그 수정판)
- `build_appendix.py` — 예외 Case/Alert 부록 페이지 생성기(구분 컬럼 자동 분류 포함)
- `verify.py` — Step 9 검증 항목(DOM/PDF/PPTX) + **R1~R8, R13~R15 재발 방지 회귀 체크**(위 1-1절)
  일괄 실행. `check_colgroup_widths`/`check_desc_overflow`/`check_indicator_el_placement`/
  `check_indicator_el_completeness`/`check_popup_backdrop_marker`/`check_desc_underflow`/
  `check_print_scale_collapse`/`check_print_only_layout_leftovers`가 R1~R8에,
  `check_template_layout_ratio`가 R13에 각각 대응하며,
  `check_all_regressions`/`print_regression_report`가 이 8개를 한 번에 실행·출력한다.
  **다른 세션이 이 문서를 열 때마다(오늘 이 세션이 끝난 뒤에도) 수정 작업의 마지막 단계로
  `verify.check_all_regressions(html_path, page)`를 반드시 실행한다** — 가이드 문서를
  읽었는지와 무관하게, 이 한 번의 함수 호출이 R1~R8, R13~R15 전체를 다시 검사해 지금까지 고친
  사고 유형이 다시 나타나지 않았는지 기계적으로 확인해 준다.

이 스크립트들은 경로를 인자로 받도록 일반화되어 있으니, 매번 새로 작성하지 말고 그대로 불러써야 한다.
**새 사고 유형을 발견하면 이 문서 1-1절과 `verify.py`에 함수(R9, R10…)를 추가하는 것을 그 세션
안에서 우선 처리한다** — "다음에 시간 날 때 정리"로 미루면 같은 사고가 그대로 재발한다.
